# 保護猫の受け入れ依頼：会話シーン第1弾

実装日：2026-10-17。参照元は作業ルートの `Docs/FutureDevelopmentPlan.md`、`Docs/UnityStandaloneIntake.md`、既存のイベント一覧・回答と記録・日常交流文・画像取得・保存処理。

## 実装範囲

4日目のナナの依頼に、導入5節→選択→迎える／見送る各4節→営業準備への復帰を追加した。依頼人とプレイヤーの話者名、地の文、既存の猫画像を表示する。穏やかな甘えん坊・のんびり屋・白黒長毛という既存設定に沿い、保護された原因や過去の飼い主など未設定の来歴は追加していない。依頼の事情は「保護猫を迎えられるかという相談」の範囲で表現した。

本文は順次表示し、同じボタンで「全文表示」から「次へ」へ切り替える。バックログは現在の会話内の既読節と現在節をスクロール表示する。結果会話には導入と確定した分岐を含める。選択肢の直近に既存DTOの費用・資金・飼育枠・加入状態・選択不可理由を表示する。人物専用画像や背景を新規制作せず、既存の店内画面と猫画像で成立させた。未登録の猫画像は既存のシルエットを使う。

`PythonIntakePanel` は単独版の場合に `IntakeConversationPanel` へ表示を委譲する。HTTP版の既存回答画面は維持する。画面は既存のイベントパネル内へ実行時に構築し、シーンのコピーや再生成を要しない。文章・話者の定義と進行モデルはUnityに依存しない `Standalone/CafeIntakeConversation.cs`、表示は `IntakeConversationPanel.cs`、ゲームルールとの橋渡しとセーブ所有は `LocalCafeConversation.cs` に分けた。紹介・派遣への拡張時も同じ進行モデルを利用できるが、その会話本文とイベント接続は今回実装していない。

## ゲームルールと停止

回答は既存の `RespondIntake` → 共通コマンド `resolve_intake` → `CafeSimulation.ResolveIntake` を使う。200の費用、支払い後の残金必須、飼育枠、休養予定での加入、見送りの費用／人気変化なし、同じ回答の冪等性と変更拒否は維持する。係数や設定JSONは変更していない。帰還待ちの回答不可条件はゲーム処理に既にあり、今回その条件を画面の選択可否にも反映した。

会話を開くと通常の自動進行を停止する。おまかせは既存の回答待ち停止を経てから会話を開き、会話終了で自動再開しない。会話中と未完了の結果会話中は、バックエンドでも営業開始・営業を進める・翌日・休業・おまかせ開始／再開／進行を拒否する。保存・読込み・他イベントの回答は受け付ける。未回答で閉じても回答を送らず、依頼の既存進行制限を維持する。他の回答待ちは閉じて先に対応できる。結果会話を閉じた場合も、イベント一覧の依頼から続きへ戻れる。結果会話の最終操作で閲覧完了にして通常画面へ戻る。

会話の開始・閲覧・終了はゲーム結果・乱数・費用・加入を変更しない。会話を開いていないAPIやルール検証では会話状態を自動作成しない。

## 保存とExtraへの接続設計

営業セーブの既存 `CafeSaveEnvelope` に任意の `conversation` を加え、ゲーム状態／ルールID／リプレイのダイジェストから分離した。スロットの既存原子的置換とバックアップを利用する。

| 項目 | 保存する内容 |
| --- | --- |
| `conversation_id` | `intake.request-cat-1.v1`。本文と節順の版を含む固定ID |
| `branch_id` | `introduction`、`accepted`、`declined` |
| `node` | 現在の節番号。導入の末尾は選択待ち、結果の末尾は終了確認 |
| `completed` | 結果を最後まで読み、会話終了を操作したか |
| `viewed_branches` | 閲覧完了の結果分岐ID。重複なし、最大1件 |

回答確定後に本文を再実行せず、保存されたゲームの回答状態から結果分岐へ同期する。料金と加入は既存の確定処理だけが行う。連打は画面の同一フレーム抑止・送信中無効化と、既存の操作ID・revision・回答の冪等性で守る。読込みは新しいコマンドepochを作る既存方式を維持する。会話ID、分岐、節範囲、閲覧完了、回答状態の整合性をロード前に検証する。不正データを拒否した場合は既存の稼働状態を維持する。

会話情報のない旧セーブは、未回答なら画面を開いた時に導入から始め、回答済みなら従来のイベント記録へ進む。旧セーブに閲覧済みを補完しない。文字の途中で保存した場合は同じ節の先頭から表示し、ゲーム上の選択や費用は戻さない。バックログは固定版の本文と節番号から再構築する。公開後の本文・節順の互換性を壊す変更はIDの版を上げ、旧版の再生定義／移行を用意する。

今回の閲覧記録は営業セーブに属する。将来のExtraでは、`conversation_id + branch_id` をキーに別の全プレイ共通プロフィールへ完了記録を集合として反映し、同じ完了通知を再処理しても重複しない構成にする。通常のスロットロードで全プレイ共通の既読を消さない。回想再生はゲームコマンドを呼ばない読み取り専用経路を別途作る。今回は共通プロフィール、タイトルExtra、CG一覧、エンディング、全体オプションを実装していない。

## 検証

最終結果は作業ルートの `Logs/StandaloneConversation` に記録する。通常プレイのセーブは使わない。実Player用の入口は `--catcafe-conversation-check <検証記録ディレクトリ>`、別プロセスでの再開検証には `--conversation-restart` を併用する。この引数がない起動では検証用コンポーネントを生成しない。

```powershell
dotnet run --project cat_cafe_sim_tool/tests/standalone/StandaloneChecks.csproj -- --conversation cat_cafe_sim_tool/unity_preview_template/Resources/CatCafeStandalone/rules.json
cat_cafe_sim_tool/build_standalone.ps1 -ProjectPath C:/Users/hi-wa/unity_workspase/CatCafeSim
```

ビルドは `Logs/StandaloneBuild/Latest/CatCafeStandalone.exe` の一組だけを使う。`Pending` から移動して置換する既存 `StandaloneBuildStorage` に従い、別ビルドフォルダやZIPは作らない。

### 最終結果

- C#検証：**147アサーション成功**。両分岐の全節でJSON保存往復、費用と加入数、回答後の連続回答、資金が費用と同額、飼育枠満員、旧セーブ、無効な分岐／節番号を確認。32シードで店舗イベントと帰還待ちの回答順序も検証した。既存の `IntakeChecks` も実行した。
- 最終Unity Player：**初回31項目、別プロセス再起動24項目成功**。Unity JSON／実ファイル／新バックエンドで導入途中・選択直前・両方の結果途中・閲覧完了を保存再開。既存 `StandaloneIntakeSmoke` の回帰検証を含み、二重支払い・加入・閲覧完了記録がないことを確認した。
- 実シーンのUGUI：全文表示と次へ、同一フレーム連打、未回答で閉じて再表示、条件による選択無効化、結果会話表示、結果を閉じてイベント一覧から再開、会話終了と通常画面への復帰、自動進行の手動再開待ち、長いバックログの末尾までのスクロールを確認した。結果会話中は営業・休業・自動進行の操作も無効になる。
- Windows実画面：1280×800、1024×768で日本語、既存ナナ画像、選択効果と条件、スクロール領域とボタンの配置を確認した。ネイティブ入力で「見送る」を選び、結果会話中の保存画面→スロット1へ確定→Player終了→再起動→ロード画面→同じ結果会話への復帰を確認。資金820と回答結果が保たれ、再回答画面へ戻らないことも確認した。バックログ末尾へスクロールバーで移動できた。
- 旧セーブ検証でUnityがnullのクラスを既定値オブジェクトとして出力する点を検出した。会話クラスの非空既定IDを廃止し、空IDの任意情報をnullとして正規化して解決。既存のルールID不一致などの読込制限は維持する。「旧セーブ対応」は既存ローダーが受理する営業セーブに会話情報がない場合を指す。
- 係数・猫定義・受け入れゲームルールは変更していない。Pythonとの全面長期比較は今回再実施せず、今回のゲームルール確認は上記の既存処理回帰と境界検証に限定した。
