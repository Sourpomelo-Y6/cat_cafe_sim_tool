# 猫・お客さんの登録と交流文制作の拡張案

2026-10-16検討。既存の猫以外の反応文や、別のお客さんのセリフをツールで制作するための設計。対象台帳からUnity連携まで実装済み。操作と検証結果は [猫・お客さんを追加して交流文を制作する](InteractionSubjectRegistry.md) を参照。以下は実装前に合意した設計と、その時点の制約。

## 方針

「対象を登録 → プロフィールを整える → 不足を確認 → 連続生成 → 校正・確認登録 → Unityへ反映」を同じ対象台帳でつなぐ。

人物のセリフは人物ごと、猫の反応文は猫ごとに持つ。人物×猫の全組み合わせへ文章を複製しない。各候補は従来どおり最大3案で、ゲーム中の行動・操作・確定反応に従って選択する。

今回の対象はまず、既存のねこじゃらし・なでる・休憩。動作の種類の追加や、新しい猫の加入・客の来店ルールの制作は別段階とする。

## 現状の制約

- `interaction_texts.py` の `SUBJECTS` がプレイヤー・佐藤さん・ミケに固定。編集・生成・検証・不足件数の計算もこれを参照している。
- 画像制作の猫一覧は `run.py` のカタログから読み込むが、交流文の対象一覧とは別。制作側の `playtest-mike` とゲーム側の `cat-mike` も異なる。
- `interaction_presentation.py` の画像対応はミケ1匹分。Unityカタログも人物2人・猫1匹・画像対応9件を前提としている。
- Unityの記録、本文・画像の選択、試作文、保存検証、画面表示にもミケへの限定がある。ツールの選択肢だけ増やしてもゲームで利用できない。
- お客さんには `guest-1` などの継続的なIDと、イベント日を含む `event-guest-日` などがある。表示名や来店履歴だけから同一人物を推測して結び付けない。

## 登録画面

メイン画面に「対象管理」を追加し、中を「猫」「人物・お客さん」に分ける。画像・文章・生成設定の各作業画面は維持する。

| 猫に保存する情報 | 人物・お客さんに保存する情報 |
| --- | --- |
| 表示名、制作対象ID | 表示名、制作対象ID、プレイヤー／お客さんの区分 |
| 特徴・性格の文章資料 | 口調、語尾、一人称、接し方、避ける表現 |
| ゲーム猫IDとの対応 | ゲームのお客さんIDとの対応 |
| 画像素材IDとの対応 | 猫の呼び方の書式、必要な個別の呼び名 |
| 既存の外見資料・基準画像への参照 | 設定済みの人物資料への参照 |
| 制作中／利用対象外の状態 | 制作中／利用対象外の状態 |

初期は既存対象から選んで追加できるようにする。猫の一覧は既存の画像カタログ、ゲームID・人物IDはゲームのルール・表示定義から読み出した参照データを使う。読み出しと対応付けを行い、元のゲーム設定は書き換えない。

新規の制作対象も登録できるが、ゲームIDが未対応なら「制作のみ」と表示する。ゲームへ反映する設定は対応付けができてから有効にする。新規登録で猫が加入したり、お客さんが自動来店したりするわけではない。

制作対象IDは初回登録時に確定し、名前変更で変えない。既存の `player`・`guest-1`・`cat-mike` は保持する。新規IDはツールで作り、ゲームIDや画像IDとは別項目で管理する。ゲームIDを同一の複数プロフィールへ曖昧に結び付けることは拒否する。

削除の代わりに、まず利用対象外にする方式を採る。本文・下書き・過去の履歴を連鎖削除せず、必要なら再び有効にできる。プレイヤーは共通の1対象を維持する。

## セリフと名前の差し込み

新しく制作する人物の共通セリフは、猫の名前を固定せず、呼び名を `{cat_call}` で表す。

| 人物 | 呼び名の設定例 | 元のセリフ | タマと交流した場合 |
| --- | --- | --- | --- |
| プレイヤー | `{cat}` | `{cat_call}、少し遊ぼうか。` | タマ、少し遊ぼうか。 |
| 佐藤さん | `{cat}ちゃん` | `{cat_call}、なでてもいいですか。` | タマちゃん、なでてもいいですか。 |

猫の反応文は `{cat}は、手元をじっと見つめた。` のように、対象猫の名前を差し込む。猫ごとの性格・反応の違いは、その猫の候補を生成して表現する。

既存の「ミケ」を含む採用済み文章は自動置換しない。従来のミケ専用素材として保持し、新しい共通素材と区別する。新しいデータ形式では人物のセリフに「どの猫でも使う／特定の猫に使う」という適用範囲を持たせ、特定猫の専用文→その人物の共通文の順で探す。任意の人物×猫の専用枠は必要になった場合だけ作り、最初から全ペアを増やさない。

名前を展開するのは実際の行動が確定した時点だけ。使える差し込み項目を限定し、任意の式やコードは評価しない。不明な項目、未対応の呼び名、展開後の文字数を検証する。保存履歴には展開後の完成文章を残すため、後から名前・呼び方を変えても過去の本文は変わらない。

## 不足を埋める画面と連続生成

台帳で追加した対象は、文章編集・画像付きプレビュー・連続生成のすべてで選べるようにする。登録直後に全対象を一斉選択せず、いま選んでいる人物・猫を初期対象にする。

| 対象1件あたり | 動作共通のみ | 操作別も含む |
| --- | --- | --- |
| 人物のセリフ | 6条件・18案 | 18条件・54案 |
| 猫の反応文 | 14条件・42案 | 50条件・150案 |

複数対象を選んだ場合は各対象の件数を足す。人物と猫の件数を掛け合わせない。

一覧には「対象／動作／操作／反応／下書き何案／登録何案／登録版との差分」を表示する。生成記録があるだけの状態は下書き・登録済みと区別する。下書きが埋まっていても未登録の条件が分かる表示にする。

「未入力のみ」は従来どおり1案でもある条件を保護する。「3案未満だけ補う」は別の選択肢として設け、既存案を入力資料に添え、空欄だけへ取り込む。既存案を含めた重複も検証する。

開始前に送信する条件一覧・条件数・案数と資料不足を表示する。資料不足は対象名付きで案内し、どこを直せば生成できるか示す。未確認の画像を観察済みとして扱わず、名前だけから性格を創作しない。

通信は引き続き1件ずつ。失敗・停止後は未完了だけ再開する。対象が増えると一度で終わらないため、この拡張では実行計画・資料の版・生成済み結果の参照を保存し、画面を閉じた後も続きを読み直せるようにする。下書きや登録済み文章への反映は確認操作を経て行う。

## データ管理と移行

- `<画像出力先>/interaction_subjects.json` を対象台帳の案とし、版・対象ID・プロフィール・ゲームID対応・画像ID対応を保持する。接続先やモデルは既存のローカル設定へ残す。
- プロフィールの編集元を台帳に集約し、単条件生成と連続生成で別の資料を持たない。既存 `interaction_llm_settings.json` の人物・猫資料を初回移行し、条件別メモは現在の設定を引き継ぐ。未移行データを勝手に上書きしない。
- 旧ミケの画像対応も台帳へ移し、以後は猫ごとの対応表から解決する。画像制作の一覧には画像素材IDを渡し、ゲームIDや制作対象IDをそのまま画像IDとして使用しない。
- 交流文とUnity向けカタログは複数対象・適用範囲・差し込みに対応する新版を用意する。対象台帳がない旧データは現在の3対象として読み込めるようにする。
- 既存の候補IDを維持し、名前変更やプロフィール変更だけでIDを作り直さない。旧条件キーで保存された候補選択履歴も新しい対応先へ結び付け、巡回を引き継ぐ。
- Unity向けには登録済みの本文と実行時に必要なID・対応・呼び名を出力する。生成用の自由記述資料や接続設定を丸ごと同梱する必要はない。
- ゲームID未対応は制作を続けられるが、実行用の対象としては書き出さず、除外件数と理由を表示する。対応済みの既存対象は通常どおり書き出せる。

## Unity側で必要な変更

1. 旧版と新版を版ごとに検証し、人物2人・猫1匹・画像9件という固定件数を廃止する。ID・対応の重複と不明参照は引き続き検証する。
2. 対象猫をカタログの登録・対応から判定し、猫名をゲームの実対象から取得する。本文、画像、保存検証、両画面にあるミケ固定処理を外す。未対応の猫へミケの専用文を流用しない。
3. 客のプロフィールIDと、実際に来店した客ID・交流セッションを分けて扱う。イベント客を共通プロフィールで制作する場合も、ゲーム側の明示的な客種別対応を使い、名前や日付を削ったIDから推測しない。この客種別共用は初期の固定ID対応の後に追加する。
4. 実行動・確定反応が一致する専用文→同じ対象・反応の操作共通文→対象名に対応した汎用文の順で補う。他の人物の口調や、別の反応条件で補わない。
5. 3案の巡回、ゲーム乱数との分離、確定本文・候補ID・版・画像参照の保存を維持する。記録済み文章の検証を現在の台帳の有効対象だけに依存させず、対象を利用対象外にした後も旧セーブを読めるようにする。
6. 取り込み・有効化・実際の読込を確認できるよう、使用中パック、登録された対象、未登録条件の補完状態をEditorから確認できる入口を設ける。前回のように検証だけして通常Playの参照先を戻した状態と区別する。

## 推奨する実装順

1. 対象台帳・登録画面・旧データ移行を実装し、既存のタマなど1匹と、別の既存客ID1人で編集対象を増やす。
2. 名前・呼び方の差し込み、猫ごとの画像対応、不足一覧と連続生成を接続する。
3. 新版の書き出し・Unity読込・多対象の本文と画像選択・両画面の表示へ接続する。ここまで通して初めて新対象のゲーム内利用が可能になる。
4. 途中再開と複数対象の制作を通しで検証し、必要に応じて客種別共通プロフィールや特定ペアの専用文を広げる。

最小の通し確認は「既存のミケ・佐藤さんを維持」「別の猫＋別の客を追加」「同じ人物の共通セリフで猫名を正しく展開」「各猫の通常・好反応・拒否・低体力を選択」「保存後の改名・利用対象外でも旧本文は同一」「客交代や猫切り替えで履歴・画像が混ざらない」「Editorの通常Playで追加した対象の3案が巡回する」とする。

設計時点では検討のみ。実装時の検証範囲と残る制限は上記の実装記録へ記載した。
