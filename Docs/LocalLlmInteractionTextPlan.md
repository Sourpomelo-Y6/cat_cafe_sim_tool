## 現状と変更範囲

`llm_generation_gui.py` と `llm_client.py` はローカルサーバーへ接続し、候補を確認して編集欄へ取り込む。通信は別スレッド、モデル一覧・JSON検証・生成記録・キャンセルがある。`text_editor_gui.py` と `content_texts.py` は猫の紹介文と normal/play/pet/sleep の4場面を下書き・確認登録する。現行プロンプトは会話不要を指定し、現行の回答検証も紹介文と4場面のみを受け付ける。

今回の交流文は既存の紹介文とは用途・条件が異なる。既存形式と生成モードを維持したまま、新しい「日常交流の文章」編集・生成モードを追加する。HTTP接続・モデル取得・非同期処理は再利用し、プロンプト・回答検証・保存形式は新しいモード用に分ける。ゲーム内でLLMを呼ばず、採用済み文章だけを書き出す。

## 制作画面の流れ

1. 制作ツールで「日常交流の文章」を開き、人物のセリフ／猫の反応／共通の行動文／地の文を選ぶ。
2. 人物または猫、行動、必要な操作・強さ、反応条件、対応する絵を選択する。
3. 特徴・口調・絵に見える状態・文章の希望を入力する。登録済みの特徴がある場合は欄へ読み込み、送信前に編集できるようにする。人物が未登録ならID・名前・口調を手入力して登録する。初期対象はプレイヤー・通常客1人・ミケ。
4. 3つの文章欄へ手入力するか、「この条件の案を3つ生成」を押す。1つの条件ごとに生成し、全人物・全行動を一度に生成しない。
5. 候補を個別に確認・修正・採用する。候補の1つだけ再生成できる構成を目指す。生成だけで採用済み文章を置き換えない。
6. 下書きを保存し、「登録内容を確認」→「確認した文章を登録」を経て採用する。
7. 組み合わせプレビューで人物のセリフ・実行動の説明・猫の反応・地の文と画像を確認し、Unity向けに書き出す。

既存編集内容が生成待ちの間に変わった場合の取り込み拒否、画面を閉じた後の結果受け取り中止、失敗時の編集保護を新モードでも維持する。接続先・モデル・入力プロフィールは保存可能にし、開き直した際に再入力する負担を減らす。

## 人物と猫を分ける理由

人物は「人物ID × 行動」ごとのセリフ約3種類を基本とする。口調・呼び方・言葉遣いを素材へ反映する。なでるのセリフが強い操作にも必ず使えるとは限らないため、候補ごとに適用できる操作・条件を設定できるようにする。

猫は「猫ID × 行動／対応する絵 × 確定した反応」ごとの描写約3種類を基本とする。通常・好反応・拒否・低体力を別条件として生成する。好意的と熱心の反応も、共用するか専用文にするかを条件で明示する。反応の良し悪しをLLMに決めさせない。

人の行動文は実際の動作・強さに対応する共通素材、地の文は場面の共通素材として持つ。人物ごとに猫の反応まで一式複製しない。人物の文と猫の文を一括生成して固定ペアにすると再利用しにくいため、部品を別生成し、組み合わせをプレビューする。

## 保存データ案

既存の `text_drafts.json`／`texts.json` と別に、交流文用の版付きJSONを用意する。名称案は `user_data/interaction_text_drafts.json`、採用先は画像出力先の `interaction_texts.json`。Unity向けの形式はJsonUtilityで読みやすい配列を使う。生成記録は既存記録と区別できる種別付きで保存する。

データを以下へ分ける。

| データ | 主な項目 |
| --- | --- |
| 人物プロフィール | 安定した人物ID、表示名、口調、呼び方、設定資料 |
| 猫プロフィール参照 | ゲーム猫IDと制作素材IDの明示的な対応、特徴・性格の資料 |
| 文章条件 | 種別、人物／猫ID、動作ID、適用操作、反応、画像・場面キー |
| 文章候補 | 安定した候補ID、本文、下書き／採用状態、必要な条件 |
| 生成記録 | 対象条件、モデル、入力、生成指示、応答、日時 |

人物の `player` や客ID、ゲーム猫ID `cat-mike` と画像制作側のIDは、名前から推測して変換せず対応表で結ぶ。行動・操作・画像キーは `interaction_scenes.py` とUnity側の定義を照合し、選べない組み合わせは登録しない。

人物IDや条件、候補IDはツール側が管理し、LLMには選択済みの条件に合う短い本文のみを返させる。条件を書き換えるモデル出力を採用しない。例として、応答は `{"variants":["案1","案2","案3"]}` のような小さなJSONに限定する。空欄・件数・文字数・重複を検証する。文字数の暫定目安はセリフ10〜40字、反応描写20〜60字。上限は画面確認後に確定する。

画像をモデルへ自動送信する前提にはしない。まず対応画像のプレビューと「前足を伸ばしている」などの状態メモを入力資料に含める。画像を直接読ませる機能は、使用モデルが対応しているかを確認した後の別段階とする。

## 生成指示と採用確認

モデルへ渡すのは、必要な人物・猫資料、行動と操作、確定反応の条件、絵の状態、文の長さ・雰囲気。人物のセリフだけを生成するときに、猫の反応結果を創作させない。猫の反応だけを生成するときは、人の会話を混ぜない。

例：ミケ／なでる／相手に合わせる／好意的／座って目を細める絵について、反応の強さを変えず言い回しと仕草の細部を変えた3案を依頼する。拒否の条件には喜ぶ描写を出さない、絵にない大きな移動や家具を加えない、猫に人間の会話をさせない、未設定の来歴を追加しない、数値変化を創作しない、と指示する。

形式検証だけでは、絵との一致や口調の自然さまで保証できない。候補を画像付きで利用者が確認し、必要なら手直しする。採用済みの候補が1つしかない条件も書き出せるようにし、3つ揃えるまで全制作を止めない。

## Unityへの接続

`unity_export.py` の既存の紹介文・画像出力を維持し、交流文カタログの別出力を追加する。新カタログがない状態でもミケの現行文章を使えるようにする。

Unityは行動結果が確定した時点で、人物・猫・動作・操作・反応・画像に合う採用済み候補から選択する。候補が複数なら直前の候補を避け、1つなら再使用する。選択はゲーム結果の乱数から分離する。履歴には完成文章と選んだ候補ID・カタログ版を保存し、表示時にカタログから文章を再組み立てしない。既存の確定本文は文章素材を編集した後も変えない。

## 推奨する実装順と確認

1. 交流文のデータ形式・人物ID登録・条件選択・手入力・下書き・確認登録。
2. 既存接続処理を使うローカルLLMの3案生成、個別取り込み、入力設定の保持。
3. 画像付き組み合わせプレビューとUnity用カタログ出力。
4. Unityで候補選択と保存履歴へ接続し、両画面を検証。

最初はプレイヤー・通常客1人・ミケ、ねこじゃらし・なでる・休憩に限定する。既存の紹介文生成を壊さないこと、編集途中の文章を失わないこと、実際のローカルLLMで3案を受け取れること、画像・反応・口調の一致、同じ文の連続回避、旧セーブと新しい保存再開の本文保持、閲覧時の状態不変を完了条件とする。人物・猫の設定資料や採用案は制作時に利用者が確認し、名前だけから性格を創作しない。
